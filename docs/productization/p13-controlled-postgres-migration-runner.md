# P13 — Controlled PostgreSQL Migration Runner

P13 adds a server-side, dependency-injected migration boundary for the canonical workspace PostgreSQL schema and tenant RLS policy.

## Scope

The runner can prepare a deterministic dry-run plan for `staging` or `preproduction`. Mutation is allowed only when the caller supplies an explicit target-bound authorization record containing an accountable approver, approval timestamp, change reference, environment, logical target database reference, and expected database name.

Before any mutation, the runner connects through the injected migration pool and verifies that `current_database()` and `current_user` exactly match the expected database and migration role. The migration role must be distinct from the application runtime role.

If authorized and the target identity matches, execution order is:

1. canonical workspace schema SQL;
2. tenant RLS SQL generated by the existing deterministic RLS generator;
3. a post-check requiring both `relrowsecurity=true` and `relforcerowsecurity=true` on the target table.

The runner returns only allowlisted target and execution metadata. Infrastructure/database exception messages, credentials, connection strings, passwords, tokens, and secret objects are not returned.

## Deliberate restrictions

- production is not a supported environment in this runner;
- no database credentials or pool construction is included;
- no automatic deployment trigger exists;
- no rollback claim is made across the separately committed schema and RLS migration transactions;
- successful application is reported as `APPLIED_NOT_PRODUCTION_CERTIFIED`;
- P12 runtime RLS/IDOR evidence must still be executed separately on an accountable selected staging target;
- backup/restore, DR, monitoring, penetration testing, PDPL/legal/professional approvals, release, merge, deployment and go-live remain external gates.

All authority flags remain false.
