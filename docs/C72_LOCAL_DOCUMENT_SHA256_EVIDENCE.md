# C72 — Client-side document bytes SHA-256; specialist source proof stays HOLD

## Actual implementation
- C70 nine reference controls remain the prerequisite: a document can be fingerprinted only after a user saves the matching reference ID for that exact specialist case and evidence type.
- Actual browser `<input type="file">` accepts locally selected PDF, PNG or JPEG up to **5 MiB**. The file size is checked before loading, and a small leading-byte signature must match the declared media type. Real `File.arrayBuffer()` reads its bytes and browser `crypto.subtle.digest('SHA-256', bytes)` hashes them. Filename and file content are never sent to an API or saved in the local Saved Deal.
- One strict saved `institutionalEvidence.specialistDocumentManifest` record contains only per-C61 evidence reference ID, category, lowercase SHA-256, byte count and MIME type; the file itself **is not uploaded** and **cannot be re-downloaded** from this record. Manifest v2 binds to project ID, valuation date, hotel/industrial class and subtype, property reference and dated C70 inventory. Earlier v1 records fail closed and require explicit reset. Changing a scoped project, valuation date or reference invalidates the manifest; no automated trust migration. These are untrusted local identifiers, not an externally witnessed case identity. Explicit clear control allows the user to delete old manifest metadata while preserving reference IDs.
- Validation refuses arbitrary fields, forged source-verification flags, duplicate control types, cross-property records, unsupported media types, over-5MiB files and header-versus-MIME mismatches. A syntactically valid SHA stored by an actor is **still not independent evidence** that the original file was hashed on a trusted device. SHA alone proves neither authorship nor document authenticity.
- C69 institutional HOLD and C70 actual C61 structural evidence HOLD are permanent; C71 prevents C5/C6 analytic export on specialist classes, even with 9/9 references and local hashes. No fabricated `CONFIRMED` source, artifact reviewer signature, licensed valuer or professional source-right evidence.
- Real Chromium tests select **actual synthetic test PDF bytes**, prove different bytes produce different digests with identical filename, reject spoofed PDF signatures, save Arabic hotel and industrial deals, reload the entire browser and reopen to verify digest/metadata persistence with no raw bytes or original filename in the stored JSON. It separately verifies **zero uploads / non-GET requests** due to local hashing, and C61/C69/C62 HOLD. Node regressions verify malformed metadata and forged source/license flags.
- Prior C71 C5/C6 legitimate **nonauthorizing** building analytic downloads and blocked specialist exports, C70 specialist reference browser flow, and C63 three building sectors run on exact-head compiled React preview, followed by build, package, nested release and security audit.

## Explicit limits — remains OPEN
- **No genuine user's source documents** were obtained in this test: PDF bytes are intentionally synthetic. The header magic check does not parse PDF pages, validate the whole file, detect malware, or prove a signature. Local hash has not been cryptographically witnessed by a trusted third party.
- No external Saudi authority, executed comparable, title validation, evidence ownership/rights, legally acceptable reviewer identity/license, storage and access-control service for real customer documents, specialized appraiser, human UAT or certified property value/report. A production-grade file-ingestion architecture needs authenticated server upload, malware scanning, encrypted evidence vault, auditable chain of custody, signed verification, redaction, retention/PDPL policy, controlled source-right proofs and external professional review.
- A draft GitHub PR triggers Cloudflare Pages automated **branch preview deployment**; the UI is accessible as a preview but no commit is merged into `main` or promoted to the production-channel by this change. Real customer confidential documents should NOT be submitted to this prototype.

## C72 hardening — acceptance and limitations
- Project ID and valuation date are required in the local hash manifest v2; copied metadata for another project or valuation date is invalid. User-controlled identifiers can still be intentionally duplicated: this is not independent chain of custody.
- Discard stale results when selected file bytes are still being read and the current case is replaced or its specialist references are edited. The browser regression deliberately pauses file reading then updates the C70 property reference.
- The regression suite additionally covers PNG/JPEG header validation, MIME spoofing, zero-length data, oversize payloads, and HTTP URL/request-body/WebSocket synthetic sentinel monitoring. This bounded check does not prove universal absence of data exfiltration.
- File headers and SHA-256 are not full PDF/PNG/JPEG structural analysis, malware inspection, official provenance, title authentication, license validation, protected repository storage, or authority to certify valuation reports.
- Keep C61/C62/C69/C71 HOLD; do not merge or deploy until the exact final head passes tests and the separate professional/legal evidence gates are resolved.
