# Post-E2I Human Learning Disposition & Change-Control Registry

Date: 2026-09-08

## Purpose

This layer governs what may happen after a verified outcome has been converted into decision-learning candidates.

The design deliberately separates:

1. verified outcome evidence,
2. learning candidate generation,
3. human interpretation,
4. human disposition,
5. change proposal creation,
6. impact assessment,
7. human approval for engineering work,
8. implementation,
9. testing and regression evidence,
10. standards/model/policy lifecycle governance,
11. release authority,
12. merge/deployment authority.

No earlier step silently grants a later authority.

## Human disposition

Every learning candidate requires an explicit human disposition:

- `ACCEPT_AS_CHANGE_CANDIDATE`
- `REJECT`
- `DEFER`

Acceptance is not implementation. Acceptance only allows creation of a scoped change proposal with an explicit `proposalRef`, `changeKind`, target and summary.

## Supported proposal classes

- `MODEL_LOGIC`
- `POLICY`
- `STANDARD_OR_RULE`
- `WORKFLOW`
- `DATA_SCHEMA`
- `DECISION_THRESHOLD`
- `ASSUMPTION_GUIDANCE`
- `DOCUMENTATION`

`STANDARD_OR_RULE` proposals are marked as requiring standards lifecycle governance.

`MODEL_LOGIC`, `POLICY` and `DECISION_THRESHOLD` proposals are marked as requiring model/policy governance.

## Impact assessment

Every accepted change proposal must have a separate impact assessment containing:

- assessor,
- timestamp,
- impact summary,
- risk level,
- affected domains,
- test-plan reference,
- rollback-plan reference,
- independent-review requirement flag.

Missing assessment keeps the registry fail-closed.

## Human approval

A fully assessed proposal still requires a separate human change approval:

- `APPROVE_FOR_ENGINEERING`
- `REJECT`
- `DEFER`

`APPROVE_FOR_ENGINEERING` means engineering proposal only. It does not authorize implementation, production activation, standards activation, release, merge, deployment or a transaction.

## Authority boundary

The registry always keeps the following false:

- `automatedPolicyUpdateAuthorized`
- `automatedModelUpdateAuthorized`
- `automatedRuleActivationAuthorized`
- `standardsActivationAuthorized`
- `productionChangeAuthorized`
- `implementationAuthorized`
- `releaseAuthorized`
- `mergeAuthorized`
- `deploymentAuthorized`
- `transactionAuthorized`

Any actual code/model/policy/standard change must occur in a separate governed change with regression evidence and the relevant lifecycle/release authority.

## Current in-app behavior

The canonical in-app path currently has no recorded human committee decision and therefore normally remains upstream at `HOLD_COMMITTEE_DECISION`. The change-control panel becomes active only when a real qualified learning review is supplied to the post-decision path.

No synthetic disposition, impact assessment or approval is generated by the UI.
